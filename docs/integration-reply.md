## 2. セキュリティルールを直しました（重要）

ご指摘をきっかけに確認したところ、**以前のルールでは「読み取り専用」として発行した
アカウントでも報告を作成でき、ステータスも変更できてしまう状態**でした
（`allow create: if request.auth != null` だったため）。

書き込めるのを、アドレスが `fm`＋数字＠`fm.example.com` のアカウント（＝店舗アカウント）
だけに限定しました。`viewer@view.example.com` は別ドメインなので弾かれます。

```
function isStoreAccount() {
  return request.auth != null
         && request.auth.token.email is string
         && request.auth.token.email.matches('^fm[0-9]{3,8}@fm[.]example[.]com$');
}
```

エミュレータで 20 項目のテストを通してあります（閲覧アカウントで作成・更新・削除が
すべて拒否されること、`fm0001@fm.example.com.evil.com` のような似たアドレスでも
書けないこと、店舗アカウントは今までどおり使えること）。

**そちらで追加のルール変更は不要です。** `trouble_reports` はこのアカウントでそのまま読めます。

## 4. 【要決定】写真の扱い — 実装前に決めてください

**ここだけ、そちらが実装に入る前に決めたいです。**

`photo_data` は Base64 なので、**1 件あたり最大 70 万文字（約 700 KB）**あります。
そして **Firestore はドキュメントの一部だけを取ってくることができません。**
一覧を読むと、写真も全部ついてきます。

- 報告 50 件の一覧 = **約 35 MB** のダウンロード
- 無料（Spark）プランの転送量は **月 10 GiB**
- スタッフ 20 人が 1 日 2 回開くだけで、1 日 1.4 GB。**1 週間で月の枠を使い切ります**

両アプリが同じデータを読むようになるので、ここは効いてきます。選択肢は 2 つです。

### 案①（暫定）: 一覧を `limit()` で絞る

そちら側だけの対応で済みます。`orderBy('created_at', 'desc')` + `limit(20)` 程度。

- ⭕ こちらの改修は不要。今日から実装に入れます
- ⚠️ それでも 20 件で約 14 MB。件数を増やせなくなります
- ⚠️ 古い報告を見る導線が作りにくい

### 案②（根治）: 写真を別コレクションに分ける

こちらでデータの持ち方を変えます。

- `trouble_reports/{id}` … 写真を除いた本体。`has_photo: true/false` を持たせる（1 件 1 KB 程度）
- `trouble_report_photos/{id}` … 写真だけ。**詳細画面を開いたときに 1 件だけ読む**

- ⭕ 一覧が 1000 倍軽くなる。件数制限が実質なくなる
- ⭕ こちらのアプリの履歴画面も軽くなる（今は同じ問題を抱えています）
- ⚠️ こちらの改修と、既存データの移行が必要（1〜2 日みてください）
- ⚠️ そちらは「一覧」と「写真の取得」を分けて書く必要があります

### こちらの考え

**案②を推します。** 運用が始まってから変えると、そちらの実装もやり直しになります。
いま決めるのがいちばん安いです。案①で始めて後から②に移るのは、二度手間になります。

**どちらで行くか返答ください。** 案②で合意できれば、こちらから先に着手して、
`has_photo` が入った状態でお渡しします。そちらはその後で実装に入ってください。
