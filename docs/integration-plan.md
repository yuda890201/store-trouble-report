# 店舗コミュニケーションアプリとの連動 — 決まったこと

先方の回答（`docs/integration-request.md` への返答）を受けて、**案B（Firestore を直接読む）** で進めます。
この文書は、こちら（不具合報告アプリ）側で何をしたかと、残っている作業をまとめたものです。

## 形

```
  不具合報告アプリ                        店舗コミュニケーションアプリ
  （store-trouble-report）                （store-communication）
                                     
  店舗アカウント fm0001 ──書く──▶ ┌──────────────────┐
                                   │ trouble_reports  │◀──読むだけ── 閲覧アカウント
  ステータス変更 ─────────────▶ └──────────────────┘              viewer@view.example.com
```

- 報告の持ち主はこのアプリ。ステータスもこちらが正（source of truth）
- コミュニケーションアプリは読むだけ。書き込みは**ルールの側で禁じてある**ので、
  実装ミスや認証情報の流出があっても報告は書き換えられない
- 写真は `photo_data`（Base64 の JPEG データ URL）に入っているので、そのまま `<img src>` に渡せる

## こちら側でやったこと

### 1. 閲覧アカウントを本当に読み取り専用にした（`firestore.rules`）

以前は「ログイン済みなら誰でも作成・ステータス変更ができる」状態だったので、
閲覧用として発行したアカウントでも報告を作れてしまいました。

書き込めるのを、アドレスが `fm`＋数字＠`fm.example.com` のアカウント（＝店舗アカウント）
だけに限定しました。閲覧アカウントは別ドメインなので弾かれます。

```
function isStoreAccount() {
  return request.auth != null
         && request.auth.token.email is string
         && request.auth.token.email.matches('^fm[0-9]{3,8}@fm[.]example[.]com$');
}
```

読み取り（`allow read`）は今までどおりログイン済みなら全件です。
コミュニケーションアプリは**全店舗の報告が見える**ので、店舗ごとの出し分けは
あちら側で `store_name` を見て行う必要があります。

### 2. ルールのテストを用意した（`tools/rules-test/`）

ルールを間違えると報告が 1 件も送れなくなるため、エミュレータ相手の自動テストを置きました。
`firestore.rules` を触ったら、本番に貼る前に `npm test` を通してください。

### 3. 仕上げを一括で行うスクリプト（`tools/finish-integration.ps1`）

```
powershell -ExecutionPolicy Bypass -File tools\finish-integration.ps1
```

次をまとめて行う。何度実行してもよい。

1. `git pull` で最新にする
2. 手元の `firestore.rules` が最新かを確認する
3. 閲覧アカウントを作る（パスワードは自動生成）
4. **そのアカウントで本番の Firestore を実際に叩き、読めること・書けないことを確かめる**
5. パスワードを埋めた回答書をデスクトップに出す

4 が肝心。ルールはエミュレータで検証してあるが、**コンソールに貼ったものが効いているか
は実際に叩かないと分からない。** 書けてしまった場合はその場で止まり、貼り直しを促す。

回答書にはパスワードが入るため、リポジトリの外にしか出力しない（出力先がリポジトリ内
だった場合はエラーで止まる）。

## 先方に渡すもの

1. `firebaseConfig` 一式（`index.html` の `FIREBASE_CONFIG` にあるもの）
2. 閲覧アカウントのアドレスとパスワード
3. Firestore のリージョン: `asia-northeast1`

## 運用で守ること

- **店舗名の表記を両アプリで完全に一致させる。** 突き合わせは `store_name` の文字列一致です。
  「渋谷店」と「渋谷　店」は別物になります。
- 店舗名はこのアプリでは端末ごとの設定（歯車 → 店舗名）です。端末を増やすたびに同じ表記で登録してください。

## 写真は別コレクションに分けた（決定・実装済み）

`photo_data` は 1 件あたり最大 70 万文字（約 700 KB）ある。Firestore は**ドキュメントの
一部だけを読むことができない**ため、写真を報告と同じドキュメントに入れておくと、
一覧を開くたびに全件の写真までダウンロードすることになる。

- 報告 50 件の一覧 = 10〜35 MB（写真の枚数と大きさによる）
- 無料（Spark）プランの転送量は月 10 GiB
- 連動すると読む側が 2 つになるので、そのままでは早い段階で枠を使い切る

そこで次の形にした。

| コレクション | 中身 | 大きさ |
|---|---|---|
| `trouble_reports/{id}` | 報告本体。`has_photo: true/false` を持つ | 1 件 1 KB 程度 |
| `trouble_report_photos/{id}` | `photo_data` だけ。**ID は報告と同じ** | 1 件 最大 700 KB |

一覧は本体だけを読むので 50 件で 50 KB 程度になる。

**不具合報告アプリ自身は写真を読まない。** 履歴には文章と「写真あり」の表示だけを出す。
写真を見るのは受け取る側の役目、という整理にした。読むのは店舗コミュニケーションアプリだけ。

### 書き込みの順番

写真 → 報告の順に書く。ID は `doc(collection(db, "trouble_reports"))` で先に決めておく。
逆順にすると、写真の保存に失敗したときに報告だけが「写真あり」で残り、利用者は
写真が送れたと思ったまま失われる。

### 古い報告について

分離前に送られた報告は `photo_data` を本体に持っている。アプリは**その形も今までどおり
表示する**ので、既存データの移行は不要。古い報告は 50 件の窓から順に外れていく。

連動先も同じ扱いにしてもらう必要がある（`photo_data` があればそれを使い、
なければ `has_photo` を見て別コレクションから読む）。

## 店舗名は選ばせる（一覧をもらった）

先方から正の一覧をもらった。

```
博多住吉通り店
清川二丁目店
```

突き合わせは文字列の完全一致なので、手入力させると全角スペースなどでずれる。
設定画面を自由入力からプルダウンに変え、`index.html` の `STORES` に持たせた。
一覧にない店舗のために「その他（自由入力）」も残してある。

**店舗が増えたら `STORES` に足す。** 先方の店舗一覧にも同じ表記で登録してもらうこと。

## 【未解決】店舗名の表記が連動先と一致していない

連動後に実機で確認したところ、**届いた報告すべてに「店舗一覧に一致なし」が付いていた。**

観測した事実:

| | |
|---|---|
| こちらが送っている値 | `博多住吉通り店` / `清川二丁目店`（`index.html` の `STORES`） |
| 先方の画面の店舗チップ | `博多住吉通り`（「店」なし） |
| 先方の報告一覧の表示 | `博多住吉通り店（店舗一覧に一致なし）` |

**末尾の「店」の有無**で外れている可能性が高いが、先方の 🏪店舗一覧 に実際に
登録されている文字列は未確認。もらった一覧（「博多住吉通り店、清川二丁目店」）と、
アプリ上の表示が食い違っている。

### いまの影響

報告そのものは届いていて、内容も写真も見えている。**店舗での絞り込みが効かないだけ。**
報告が消えることはない（先方は一致しない場合も文字列を出す作りにしてある）。

### 保留の理由

店舗名の表記ゆれは、このアプリと店舗コミュニケーションアプリだけの問題ではなく、
**他の自作アプリでも表記が違う可能性がある。** 2 アプリ間で辻褄を合わせるより、
どこかで表記を決めて全アプリで揃えるほうがよい。別途まとめて扱う。

### 直すときに触る場所

- `index.html` の `STORES`（設定画面のプルダウンの選択肢）
- 各端末の設定（歯車 → 店舗名）を選び直す必要がある
- 先方の 🏪店舗一覧 側を変える場合は、先方の既存データへの影響を確認すること
